# Combine Harvester Pattern For Reading Memory

Date: 2026-05-30

## Focus

Explore how to adapt the "combine harvester" pattern to Reading Memory: long-running agent work maintains durable state in a simple artifact that records instructions, progress, decisions, and next steps.

The goal is not generic project management. It is making reading-corpus workflows resumable, auditable, and inspectable across agents and sessions.

## Grounding

Reading Memory already has the right corpus boundary:

- `/ingest` preserves durable reading items.
- `/query` recalls saved reading.
- `/brief-guide` selects candidates.
- `/brief-events` records brief inclusion and skip outcomes.
- SQLite stores corpus facts, Flue analysis, idempotency, activity, and brief events.

The missing piece is not "remember articles." It is durable run state for multi-step reading operations:

- newsletter triage
- morning brief assembly
- failed ingest recovery
- corpus audits
- model/ranking/eval changes
- source dedupe investigations

## Ranked Ideas

### 1. Reading Run Ledger

Add a first-class "run ledger" concept for any multi-step Reading Memory workflow. A run records:

- goal
- source window or input set
- operator/agent
- current phase
- decisions made
- items considered
- items ingested, skipped, archived, or deferred
- verification performed
- next recovery step

This should start as a local markdown or JSONL artifact generated by calling agents, not a service endpoint. It is the fastest way to get value without expanding the API.

Why it survives: it directly solves the observed failure mode from newsletter triage: inbox actions, summaries, captures, and verification were spread across chat, temp files, and DB state.

### 2. `runs/` Scratch Convention Plus Resume Prompt

Define a repo/workspace convention:

```text
~/.reading-api/runs/<yyyy-mm-dd>-<slug>/
  run.md
  inputs.json
  decisions.jsonl
  outputs.json
```

`run.md` is human-readable and agent-readable. `decisions.jsonl` is append-only. `outputs.json` is machine-friendly for later audit or replay.

Add a bundled prompt/skill instruction: "Before continuing a Reading Memory operation, read the latest run ledger and resume from `next_step`."

Why it survives: the pattern is portable across OpenClaw, Codex, Claude Code, and future MCP clients. It does not require every runtime to share conversation memory.

### 3. Run Ledger Events In SQLite

After the markdown convention proves useful, add a small service-backed `run_events` table and endpoint:

- `POST /runs`
- `POST /runs/:id/events`
- `GET /runs/:id`
- `GET /runs/recent`

Events would cover `considered`, `ingested`, `skipped`, `included`, `archived_done`, `verified`, `blocked`, and `resumed`.

Why it survives: it makes runs queryable and keeps operational state near corpus state. But it should not be the first move because it adds API and migration surface.

### 4. Morning Brief / Newsletter Triage Integration

Use run ledgers specifically for newsletter and morning brief workflows:

- Every fetched newsletter becomes a `considered` event.
- Every saved item links to its `item_id`.
- Every "mark Done" action records message id, subject, rationale, and verification result.
- Every non-capture records why it was not worth preserving.

Why it survives: this is where the pattern immediately pays rent. It turns "what did we just do?" into inspectable state.

### 5. MCP Adapter For Reading Memory Tools

Build a thin MCP server around existing HTTP endpoints:

- `reading_search`
- `reading_ingest`
- `reading_brief_guide`
- `reading_record_event`
- `reading_get_item`
- eventually `reading_get_run` / `reading_append_run_event`

Expose run ledgers as MCP resources and common workflows as prompts. Official MCP docs frame tools as model-invoked actions, resources as context/data, and prompts as user-controlled templates; that maps cleanly onto Reading Memory.

Why it survives: this makes Reading Memory portable across clients without changing the backend. It should follow the run-ledger convention, not precede it.

### 6. Recovery-Oriented Eval

Add an eval fixture for interrupted operations:

1. start a mock newsletter triage run
2. record partial considered/ingested/skipped events
3. simulate context loss
4. ask a fresh agent to resume
5. assert it does not duplicate ingestion, re-archive wrong items, or lose the intended read queue

Why it survives: the combine-harvester pattern is only real if fresh agents resume correctly. Otherwise it is just documentation.

## Rejected Ideas

### Full Human-Facing Task App

Too much surface area. Reading Memory is intentionally a backend harness, not a UI.

### Store Run State Only In Conversation Memory

This is exactly the failure mode the pattern is meant to avoid. Conversation recall is useful evidence, not an operational source of truth.

### Make Every Reading Item A Run

Too noisy. Runs should represent multi-step workflows, not individual article captures.

### Add MCP Before Run Semantics Exist

MCP would expose whatever semantics exist. If the semantics are thin, the adapter only standardizes thinness.

### Replace `/brief-events` With Generic Run Events

Brief events are corpus facts with resurfacing semantics. Run events are operational facts. They should relate, not collapse into one table too early.

## Recommended Sequence

1. Add a documented run-ledger convention and one helper script for creating a run directory.
2. Use it manually for the next newsletter triage or morning brief recovery.
3. Add tests/evals around resume behavior once the shape stabilizes.
4. Promote to SQLite endpoints only after 2-3 real runs show stable event names.
5. Add an MCP adapter after the HTTP/run semantics are clear.

## One-Sentence Product Frame

Reading Memory should not only remember what was worth reading; it should remember how a reading workflow reached its decisions so any future agent can resume without reconstructing the work from chat.
